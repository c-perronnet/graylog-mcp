<objective>
Ship the 5 pipeline CRUD tools (PIPE-01..PIPE-05). Every mutating tool routes the pipeline source through `POST /api/system/pipelines/pipeline/parse` BEFORE returning the request descriptor — Graylog's grammar is authoritative; the wrapper refuses apply on ParseException via `reason: "pipeline_parse_failed"`. `update_pipeline` follows STRICT_NO_ECHO per 04-U1-SMOKE.md (Plan 01's decision artifact); parse pre-flight fires ONLY when `args.changes.source` is present (no-op title/description updates skip the round-trip).

Purpose: This plan lands the simpler half of the rule-vs-pipeline DSL story — pipelines have no structured-intent grammar (PIPE-03 accepts raw DSL only per CONTEXT.md §"Deferred Ideas"), no cascade pre-flight (PIPE-05 is a simple delete; orphaned stream connections become recoverable garbage per CONTEXT D-15), no mutable flag (D-15 — pipelines are user-created, no `is_editable` defense). The interesting safety thesis is the parse pre-flight + STRICT_NO_ECHO; landing them here means Plan 03's rule CRUD can compose against the same parse-preflight helper.
